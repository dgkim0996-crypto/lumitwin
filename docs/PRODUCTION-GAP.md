# 현업 적용까지 남은 것

LumiTwin은 실제 공장 MES와 **같은 구조**로 핵심 흐름을 끝까지 만든 포트폴리오입니다. 설비 → 엣지 → MES → DB → 화면으로 데이터가 흐르고, 화면의 조작이 다시 설비까지 갑니다. 하지만 실제 라인에 바로 넣을 수 있는 제품은 아닙니다. 이 문서는 무엇이 이미 현업 구조와 같고, 현업에 넣으려면 무엇이 더 필요한지를 코드 근거와 함께 적습니다.

판단 기준은 하나입니다. **이 시스템이 멈추거나 틀렸을 때 실제 라인과 제품에 무슨 일이 생기는가.** 시연에서는 데이터가 조금 빠져도 되지만, 현장에서는 추적성 기록 한 줄이 빠지면 리콜 범위를 못 정합니다.

## 1. 한눈에 보기

| 영역 | 지금 LumiTwin | 현업에 넣으려면 |
|---|---|---|
| [설비 연결](#31-설비-연결) | SimPy 시뮬레이터, 가상 PLC(OPC UA, 보안 없음) | 실제 PLC·장비별 통신, 태그 매핑, 설비망(OT) 분리, 통신 보안 |
| [상위 시스템](#32-상위-시스템-erpwms) | 작업지시를 MES 안에서 자동 계획 | ERP 생산계획·BOM·자재 입출고 연동, 자재 재고 |
| [기준정보](#33-기준정보) | 공정·규격·라우팅이 코드에 있음 | 화면에서 관리, 변경 승인·버전 이력 |
| [현장 기기](#34-현장-기기) | 시리얼을 시뮬레이터가 만듦 | 바코드 스캐너, 라벨 프린터, 작업자 단말 |
| [장애 대응](#35-장애-대응과-가용성) | MES 한 프로세스에 브로커까지, 큐는 메모리, 백업 없음 | 이중화, 영속 큐, 백업·복구, 장애 시 라인 정책 |
| [데이터 규모](#36-데이터-규모와-보관) | 며칠 시연에 DB 약 850 MB, 보관 정책 없음 | 파티셔닝, 보관 연한, 시계열 저장소, 실제 규모 부하 시험 |
| [보안·계정](#37-보안과-계정) | 시연 계정 5개, 자체 비밀번호, 브로커 인증 없음 | 사내 계정(AD/SSO), 계정 수명 관리, OT 보안 |
| [값의 근거](#38-값의-근거) | 공장 정의 수치의 약 59 %가 가정값 | 실제 라인 데이터로 보정 |
| [고객사 요구](#39-고객사-요구와-품질-문서) | 관리계획서는 공장 정의에서 자동 생성 | PFMEA 연결, 고객사별 추적성·라벨 요구 |
| [검증·운영](#310-검증과-운영) | 노트북 한 대에서 10분 측정, 자동 테스트 | 며칠 연속 운전, 모니터링·경보, 한 라인 시범 적용 |

## 2. 이미 현업 구조와 같은 것

현업에 넣을 때 **버리지 않고 그대로 키울 수 있는** 부분입니다.

- **계층 구조**: 설비(PLC) → 엣지 게이트웨이 → 메시지 브로커 → MES → DB → 화면. ISA-95의 레벨 1~3 구분과 같습니다. 설비 쪽만 바꾸면 위 계층은 그대로 씁니다.
- **엣지의 끊김 대비**: OPC UA 경로의 엣지는 MQTT가 끊기면 상태·실적을 버퍼에 쌓았다가 다시 붙으면 순서대로 보냅니다(store and forward, 최대 2만 건, `sim/lumisim/edge.py`).
- **인터록 판정**: 게이트 설비가 투입 전에 묻고, MES가 Hold → 불량 미처리 → 재검사 순서 → 공정 순서 → 작업지시 → 초물 순으로 판정합니다. 응답은 메모리에서 바로 하고 DB 기록은 뒤따라 써서, 수집 경로가 DB를 기다리지 않습니다(p95 1.0 ms, [docs/perf](perf/README.md)).
- **실행 MES 흐름**: 작업지시와 기종 변경, NCR과 MRB, 수리 뒤 재검사, Hold와 영향 범위, 4M 변경점과 초·중·종물이 서로 이어져 있습니다([docs/MES.md](MES.md)).
- **권한과 기록**: 역할별 권한(`@Perm`), 쓰기 조작의 감사 기록(누가·언제·실제/가상 시각·무엇을, `/audit`), 로그인 시도 제한.
- **검증 습관**: 자동 테스트(shared 19, server 188, sim 71), 화면 E2E 30개, CI, 부하 측정 스크립트, 측정으로 병목을 찾아 고친 기록.

## 3. 영역별 차이

### 3.1 설비 연결

**지금**
- 설비는 SimPy 시뮬레이터입니다. OPC UA 경로에서는 시뮬레이터가 가상 PLC 노릇을 하고, 엣지가 태그를 읽어 MQTT로 올립니다.
- 가상 PLC는 보안 정책 None, 익명 접속만 엽니다(`sim/lumisim/opcua_plc.py`).
- 태그 이름과 의미는 공장 정의에서 자동으로 정해집니다.

**현업에서는**
- 설비 제조사와 연식마다 통신 방식이 다릅니다. PLC는 제조사 전용 프로토콜(예: MC 프로토콜)이나 Modbus를 쓰는 경우가 많고, SMT 장비는 반도체·전자 업계 표준(SECS/GEM)이나 장비사 로그 파일로 데이터를 줍니다. OPC UA를 지원하지 않는 오래된 설비도 흔합니다.
- 설비마다 수백~수천 개 태그를 "이 주소가 무슨 값인가"로 매핑하는 작업이 가장 오래 걸립니다. PLC 프로그램을 만든 사람과 같이 해야 합니다.
- 설비망(OT)과 사무망(IT)은 분리하고, 그 사이에서 엣지만 양쪽에 붙게 둡니다. OPC UA는 서명·암호화(Basic256Sha256)와 인증서를 씁니다.
- 설비 시계와 서버 시계를 맞춥니다(NTP). LumiTwin은 시뮬레이터의 가상 시계를 기준으로 삼습니다.

### 3.2 상위 시스템 (ERP·WMS)

**지금**
- 작업지시는 MES 안에서 만듭니다. 대기 건이 3건보다 적으면 자동 계획이 기종을 번갈아 채웁니다(`server/src/execution/planner.ts`).
- 자재 LOT는 시뮬레이터가 만들고, 재고·입고·출고 개념은 없습니다.

**현업에서는**
- 생산계획과 BOM은 ERP에서 내려오고, MES는 받은 계획을 라인별 작업지시로 풀어 실행한 뒤 실적(양품·불량·자재 사용)을 다시 ERP로 올립니다.
- 자재는 창고 관리(WMS)에서 입고 검사를 거쳐 라인에 불출됩니다. 투입할 때 자재 바코드를 찍어 "이 LOT가 이 작업지시에 맞는가"를 확인하는 것도 인터록입니다.
- 두 시스템 사이 인터페이스는 실패했을 때 다시 보내기, 중복 막기, 대사(양쪽 수량 맞추기)까지 설계해야 합니다.

### 3.3 기준정보

**지금**
- 공정, 설비, 사이클 타임, 측정 항목과 규격, 불량 코드와 처리 기준, 라우팅이 모두 코드(`shared/src/factory/*.ts`)에 있습니다. 바꾸려면 코드를 고치고 빌드한 뒤 다시 띄웁니다.
- 관리계획서는 이 정의에서 자동으로 만들어져 정의와 어긋나지 않는다는 장점이 있습니다.

**현업에서는**
- 기준정보는 생산기술·품질 담당자가 화면에서 관리합니다. 규격 하나를 바꿔도 승인을 거치고, 언제부터 어떤 값이 적용됐는지 버전 이력이 남아야 합니다. 그래야 "이 제품을 만들 때 규격이 무엇이었나"에 답할 수 있습니다.
- LumiTwin의 4M 변경점은 "설비에서 바뀐 것"을 잡지만, 기준정보 자체의 변경 관리(설계 변경)는 없습니다.

### 3.4 현장 기기

**지금**
- 시리얼과 자재 LOT는 시뮬레이터가 만들어 메시지에 담습니다.
- 작업자 태블릿 화면(`/operator`)은 있지만 바코드나 라벨과는 연결되지 않습니다.

**현업에서는**
- 투입할 때 제품·자재 바코드를 스캐너로 찍고, 공정이 끝나면 라벨 프린터로 시리얼 라벨을 뽑습니다. 완제품 라벨 형식은 고객사가 정하는 경우가 많습니다.
- 작업자 단말은 장갑을 낀 손, 소음, 밝은 조명에서 써야 해서 버튼 크기와 확인 절차를 현장에서 다시 다듬습니다.

### 3.5 장애 대응과 가용성

가장 큰 차이입니다. 시연에서는 "가끔 빠져도 되는" 것이 현장에서는 라인 정지나 추적성 구멍이 됩니다.

**지금**
- **브로커가 MES 안에 있습니다.** MQTT 브로커(aedes)가 NestJS 서버 프로세스 안에서 돌고 메시지를 디스크에 남기지 않습니다(`server/src/mqtt/mqtt-broker.service.ts`). MES가 재시작하면 브로커도 같이 내려갑니다. 그동안 시뮬레이터 직접 경로는 MQTT 클라이언트 큐(최대 2,000건, `sim/lumisim/mqtt_io.py`)에만 기대고, OPC UA 경로의 엣지는 최대 2만 건까지 쌓았다가 넘치면 오래된 것부터 버립니다.
- **인터록이 답하지 않으면 통과합니다.** 인터록 응답은 3초 안에 와야 합니다. 3번 연달아 시간 초과면 시뮬레이터는 MES가 멈춘 것으로 보고, 응답이 다시 올 때까지 확인 없이 통과시키며 그 개체에 `ilkSkip` 표시를 남깁니다(`sim/lumisim/engine.py`의 `ILK_BYPASS_AFTER`). MES가 다시 뜨면 메모리 상태를 DB에서 되살리는 동안 `WAIT`로 답합니다.
- **DB 기록 큐가 메모리에 있습니다.** DB가 느려지면 기록이 최대 5만 건까지 메모리에 쌓이고, 넘치면 오래된 것부터 버립니다(`server/src/production/production.writer.ts`). 부하 측정에서는 한 건도 버리지 않았지만, 프로세스가 죽으면 큐에 있던 기록은 사라집니다.
- **서버 한 대, 백업 없음.** 배포는 VM 한 대에 pm2로 띄웁니다. 배포 스크립트에 DB 백업은 없습니다.

**현업에서는**
- 브로커는 MES와 분리하고 이중화합니다. 메시지는 디스크에 남기고, 품질 기록은 QoS 1 이상이나 영속 큐(예: Kafka, DB outbox)로 보내 "적어도 한 번"을 보장한 뒤 MES에서 중복을 거릅니다.
- **MES가 멈췄을 때 라인이 어떻게 할지는 기술이 아니라 경영 결정입니다.** 멈추면 생산 손실, 통과시키면 품질 위험입니다. 보통 공정별로 정합니다. 예를 들어 안전·법규 특성이 걸린 공정은 멈추고, 나머지는 통과시킨 뒤 `ilkSkip` 개체를 나중에 모두 다시 판정합니다. LumiTwin은 통과 정책 하나만 있고, 다시 판정하는 화면은 없습니다.
- MES 서버와 DB는 이중화하고, 백업과 **복구 훈련**(실제로 되살려 보기)을 정기적으로 합니다. 복구 목표 시간과 허용 데이터 손실을 먼저 정합니다.
- 서버를 고칠 때 라인을 멈추지 않게 무중단 배포와 DB 마이그레이션 절차가 필요합니다.

### 3.6 데이터 규모와 보관

**지금**
- 60배속 10분에 약 8만 3천 건을 씁니다. 며칠 시연한 DB가 약 850 MB이고, 상태 기록(`state_event`)만 약 240만 행입니다.
- 지운 적이 없고, 보관 기간이나 파티션도 없습니다. 실행(run)마다 기록을 나눠 둘 뿐입니다.
- 부하 측정은 3라인 40대 규모를 노트북 한 대에서 쟀습니다([docs/perf](perf/README.md)).

**현업에서는**
- 공장 하나에 설비가 수백 대이고 24시간 돌아갑니다. 메시지 양이 지금보다 한 자릿수 이상 많을 수 있어, 목표 하드웨어에서 실제 규모로 다시 재야 합니다.
- 추적성 기록은 고객사 요구에 따라 여러 해 보관하는 경우가 흔합니다. 시간 단위로 표를 나누고(파티셔닝), 오래된 기록은 싼 저장소로 옮기되 조회는 되게 합니다.
- 진동·전류 같은 고빈도 센서 값은 시계열 저장소로 분리하고, 화면용 집계는 교대 단위로 미리 만들어 둡니다(롤업). 지금은 에너지·보전 집계를 요청할 때 계산하고 짧은 캐시로 버팁니다.

### 3.7 보안과 계정

**지금**
- 시연 계정 5개(작업자·조장·품질·보전·관리자)와 자체 비밀번호를 씁니다. 비밀번호는 scrypt로 저장하지만 매개변수가 Node 기본값이라 OWASP 권장보다 낮습니다(코드에 `weak` 표시, `server/src/auth/auth.core.ts`).
- 로그인 쿠키는 8시간 유지되고 HMAC으로 서명합니다. 로그인은 IP별 1분 10번으로 막습니다.
- MQTT 브로커에는 인증이 없습니다. 배포에서는 `MQTT_BIND=127.0.0.1`로 같은 서버에서만 붙게 해 막습니다.
- 공개 주소는 보기 전용이 먼저 막고, 제어 키를 넣어야 로그인할 수 있습니다.

**현업에서는**
- 사내 계정(AD·SSO)으로 로그인하고, 입사·부서 이동·퇴사에 따라 권한이 자동으로 바뀌어야 합니다. 관리자 계정은 2단계 인증을 씁니다.
- 브로커와 OPC UA에 인증서 기반 인증과 암호화를 켭니다. 엣지마다 다른 자격 증명을 줍니다.
- 설비망 보안은 IEC 62443 같은 산업 제어 시스템 보안 기준을 따릅니다.

### 3.8 값의 근거

**지금**
- 공장 정의의 수치(사이클 타임, 불량률, 규격, 소비 전력 등)에는 근거 등급이 붙어 있습니다. 라인 정의 파일(`hl.ts`·`em.ts`·`osm.ts`) 기준으로 약 270개 중 **확인 38개(약 14 %), 근거 약함 73개(약 27 %), 가정 161개(약 59 %)** 입니다.
- 실제 SL 데이터는 쓰지 않았습니다. 공개 자료와 업계 일반 자료로 만들었습니다([docs/research](research)).

**현업에서는**
- 가정값은 첫 몇 주의 실제 데이터로 바꿉니다. 특히 사이클 타임과 고장 간격(MTBF)은 OEE와 예지 보전 경고 기준에 직접 들어가서, 가정값 그대로면 경고가 너무 많거나 너무 늦습니다.
- 근거 등급을 남겨 둔 구조는 그대로 쓸 수 있습니다. 실제 값으로 바꾼 항목을 `confirmed`로 올리면 됩니다.

### 3.9 고객사 요구와 품질 문서

**지금**
- 관리계획서(`/control-plan`)는 공장 정의에서 자동으로 만들어지고, 특별 특성 기호와 근거 등급을 함께 보여 줍니다.
- 4M 변경점, 초·중·종물, NCR·MRB 흐름은 IATF 16949의 일반적인 요구를 따라 만들었습니다.

**현업에서는**
- 관리계획서는 PFMEA(공정 고장 모드 영향 분석)와 연결되어야 합니다. 어떤 고장 모드 때문에 이 특성을 이 주기로 관리하는지가 이어져야 감사에서 설명할 수 있습니다. LumiTwin에는 PFMEA가 없습니다.
- 완성차 고객사마다 추적성 범위, 라벨 형식, 부적합 보고 양식, 변경 신고 절차가 다릅니다. 고객사 요구서를 받아 화면과 기록 항목을 맞춥니다.

### 3.10 검증과 운영

**지금**
- 자동 테스트와 화면 E2E는 기능이 맞는지 봅니다. 부하 측정은 10분입니다.
- 서버 상태는 pm2 로그와 화면의 연결 표시로만 봅니다. 지표 수집이나 경보는 없습니다.
- 실제 작업자가 써 본 적이 없습니다.

**현업에서는**
- 며칠~몇 주 연속 운전으로 메모리가 새는지, DB가 어떻게 커지는지, 시계가 밀리는지 봅니다. 네트워크를 일부러 끊어 보는 장애 시험도 합니다.
- 서버·브로커·DB·엣지 상태를 지표로 모으고(예: Prometheus), 기록 큐가 쌓이거나 엣지가 끊기면 담당자에게 경보가 갑니다.
- 한 라인에서 먼저 시범 적용하고, 작업자·조장·품질 담당의 피드백으로 화면과 절차를 고친 뒤 넓힙니다.

## 4. 현업에 넣는다면 이 순서로

라인을 멈출 위험이 없는 것부터, 데이터를 믿을 수 있게 된 다음에 막는 기능을 켭니다.

| 단계 | 하는 일 | 왜 이 순서인가 |
|---|---|---|
| 0. 현장 조사 | 공정·설비 목록, 설비별 통신 방식, 기존 시스템(ERP·WMS·기존 MES), 고객사 요구서를 모은다 | 설비 연결과 인터페이스 범위가 일정의 대부분을 정한다 |
| 1. 한 라인 수집만 | 설비 연결과 기준정보만 넣고 실적·상태를 **읽기만** 한다. 가정값을 실제 값으로 바꾼다 | 라인에 영향이 없다. 화면 숫자가 현장 감각과 맞는지 먼저 확인한다 |
| 2. 추적성 | 바코드 투입·라벨 발행, 시리얼 계보를 켠다 | 막는 기능보다 기록이 먼저다. 기록이 맞아야 판정도 맞다 |
| 3. 인터록을 경고로 | 인터록을 켜되 막지 않고 "막았을 경우"를 기록만 한다 | 잘못 막으면 라인이 선다. 오판정 비율을 먼저 본다 |
| 4. 인터록을 차단으로 | 공정별로 차단을 켜고, MES 장애 시 정책(멈춤·통과 뒤 재판정)을 정한다 | 경고 모드에서 오판정이 충분히 낮아진 공정부터 |
| 5. ERP 연동·작업지시 | 생산계획을 받아 작업지시로 풀고 실적을 올린다 | 현장 실적이 믿을 만해진 뒤라야 ERP에 올릴 수 있다 |
| 6. 운영 체계·확대 | 이중화, 백업·복구 훈련, 모니터링·경보를 갖추고 다른 라인으로 넓힌다 | 라인이 MES에 기대기 시작하면 멈춤이 곧 생산 손실이다 |

## 5. 면접에서 이렇게 답한다

**"이거 실제 라인에 바로 쓸 수 있나요?"**
> 아니요. 현업 MES와 같은 구조로 핵심 흐름을 끝까지 만들고 숫자로 검증한 것입니다. 실제로 넣으려면 설비별 통신과 태그 매핑, ERP 연동, 기준정보 관리, MES가 멈췄을 때의 라인 정책, 데이터 보관 설계가 더 필요합니다.

**"가장 먼저 고칠 약점은 뭔가요?"**
> 장애 대응입니다. 지금은 브로커가 MES 프로세스 안에 있고 DB 기록 큐가 메모리에 있어서, MES가 죽으면 그 사이 기록이 빠질 수 있습니다. 브로커를 분리하고 품질 기록은 영속 큐로 보내 적어도 한 번 전달을 보장하겠습니다.

**"MES가 멈추면 인터록은 어떻게 되나요?"**
> 지금은 3번 연달아 응답이 없으면 확인 없이 통과시키고 그 개체에 표시를 남깁니다. 시연이 멈추지 않게 고른 정책입니다. 현장에서는 멈출지 통과시킬지를 공정별로 정해야 하고, 통과시킨 개체를 나중에 다시 판정하는 절차가 함께 있어야 합니다.

**"현장에 넣는다면 어디부터 하겠습니까?"**
> 한 라인에서 수집만 먼저 하겠습니다. 라인에 영향 없이 화면 숫자가 현장과 맞는지 확인하고 가정값을 실제 값으로 바꾼 뒤, 추적성, 경고 모드 인터록, 차단 순서로 켜겠습니다.
