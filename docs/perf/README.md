# 성능 측정 기록

`scripts/loadtest.mjs`로 잰 결과와, 측정으로 찾은 병목을 고친 과정을 남긴다. 숫자를 다시 재려면 앱을 운영 빌드로 띄우고(`npm run build` → `npm start`) 아래를 돌린다.

```bash
node scripts/loadtest.mjs --minutes 10 --users 20 --api-seconds 30 --speed 60 --out docs/perf/loadtest-60x-10min.json
```

## 측정 환경

- 노트북 한 대: AMD Ryzen 5 7430U(6코어 12스레드), 메모리 14 GB, Windows 11
- 운영 빌드 전체를 같은 PC에서: 시뮬레이터(SimPy, 공장 3라인 40대) + MQTT 브로커 + NestJS MES + 내장 PostgreSQL + Next.js
- 60배속(실제 1초 = 가상 1분), MQTT 경로
- DB는 비우지 않은 상태 (상태 기록 `state_event` 약 240만 행, 공정 기록 약 90만 행, DB 약 850 MB)

## 무엇을 재나

| 항목 | 재는 법 |
|---|---|
| 인터록 응답 시간 | 브로커에 붙어 `ilk/req`와 `ilk/res`를 엿듣고 같은 `reqId`끼리 시간 차를 잰다 |
| 시뮬레이터 배속 유지 | 가상 시간 진행 ÷ 실제 시간 ÷ 배속 (100 %면 밀리지 않음) |
| MES 수신·DB 기록 | 서버가 받은 메시지 수, 기록 큐의 대기·버림 건수, 서버 프로세스 메모리 |
| 조회 API | 동시 사용자 N명이 화면 조회 API 12개를 번갈아 쉬지 않고 부른다 (생각 시간 없음, 닫힌 고리) |

## 병목을 찾고 고친 과정

처음 측정(2026-11-13, 같은 조건)에서 조회 API가 느렸다.

| 끝점 | 처음 p50 / p95 (ms) | 캐시 뒤 p50 / p95 (ms) |
|---|---|---|
| `/energy` | 1,589 / 2,939 | 12 / 206 |
| `/maintenance` | 940 / 2,813 | 10 / 45 |
| `/production/defects` | 247 / 1,905 | 32 / 49 |
| `/reports/shifts` | 226 / 1,343 | 21 / 40 |
| `/production/units?limit=50` | 122 / 1,274 | 28 / 43 |
| `/changes` | 92 / 1,129 | 21 / 37 |
| `/maintenance/health` | 326 / 845 | 18 / 45 |
| `/live/snapshot` | 134 / 692 | 15 / 41 |
| `/live/spc` | 220 / 662 | 9 / 20 |
| `/orders` | 138 / 618 | 9 / 21 |
| `/live/losses` | 30 / 582 | 10 / 21 |
| `/ncr` | 46 / 473 | 9 / 22 |
| **전체** | **235 / 2,087** (초당 41건) | **15 / 40** (초당 1,033건) |

1. **찾기**: 끝점별로 나누니 `/energy`와 `/maintenance`가 유난히 느렸다. 둘 다 요청마다 이번 실행의 설비 상태 기록(`state_event`)을 처음부터 읽어 구간 길이를 더한다. 실행이 길어질수록 느려지는 구조다.
2. **원인**: 이 둘이 DB 연결과 Node 이벤트 루프를 오래 잡아, 원래 가벼운 `/orders`·`/ncr`까지 줄을 섰다. 그래서 다른 끝점의 p95도 수백 ms~1초대였다.
3. **고치기**: 두 집계에만 짧은 캐시를 넣었다 (`server/src/common/ttl-cache.ts`). 에너지 3초·보전 2초 동안 같은 질의 결과를 같이 쓰고, 계산 중에 같은 질의가 또 오면 새로 계산하지 않고 진행 중인 결과를 기다린다. 실패한 결과는 캐시에 남기지 않는다. 화면은 몇 초마다 다시 읽으므로 2~3초 늦은 값은 문제가 되지 않는다.
4. **다시 재기**: 같은 조건에서 전체 p95가 2,087 → 40 ms, 처리량이 초당 41 → 1,033건이 됐다. 느린 두 끝점이 줄을 막지 않으니 나머지 끝점도 같이 빨라졌다. 인터록 최대 응답도 2,227 → 95 ms로 줄었다 (같은 서버 프로세스가 조회와 인터록을 같이 처리하기 때문).

## 한계

- 같은 PC에서 부하 발생기와 서버가 CPU를 나눠 쓴다. 서버만 따로 두면 숫자는 더 좋아질 수 있다.
- 캐시는 계산 횟수를 줄일 뿐 한 번 계산하는 시간은 그대로다. 실행이 아주 길어지면 첫 계산이 느려지므로, 그때는 교대 단위로 미리 집계해 두는 표(롤업)가 다음 단계다.
- Oracle 상시 무료 서버(ARM 2코어·4 GB)에서는 아직 재지 않았다.
